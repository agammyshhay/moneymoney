Security & Privacy Audit Report

MoneyMoney Desktop App (Electron)
Audit Date: April 2026

Executive Summary

MoneyMoney handles extremely sensitive data: Israeli bank login credentials (usernames, passwords, card numbers), financial transactions, and API authentication tokens. This audit identified 16 security vulnerabilities across the Electron main process, preload bridge, renderer, build pipeline, and data storage layers.

The most critical findings involve weak encryption key derivation that protects all bank credentials, a missing Content Security Policy that leaves the app open to XSS attacks, a disabled Chromium sandbox, and unsigned auto-updates that could allow malware injection.

Critical Vulnerabilities

1
Hardcoded Encryption Password
packages/main/src/backend/configManager/encryption/crypto.ts:17
Critical
▼

What's Wrong

The encryption key that protects ALL user data (bank passwords, card numbers, API tokens) is derived using a hardcoded string 'moneymoney'. Since the source code is public on GitHub, anyone who obtains a user's encrypted config file can decrypt it immediately.

function deriveKey(salt: string): Buffer { return crypto.scryptSync(salt, 'moneymoney', 32); // hardcoded password! }

Attack Scenario

1. Malware, a malicious app, or another user on the same machine reads the config.encrypt file from %AppData%.
2. Attacker reads the salt from the OS keychain (if they have user-level access) or brute-forces it.
3. Using the known password 'moneymoney' + salt, they decrypt all bank credentials instantly.

Fix Complexity

Medium

Replace the hardcoded string with a randomly generated key stored in OS keychain (keytar). Requires a migration step that re-encrypts existing configs on first launch. Estimated: 1-2 days of development + testing.

Usability Impact

Minor

Users won't notice any difference. The migration happens transparently on app startup. Only edge case: if a user manually copies their config file to another machine, they'll need to re-enter credentials.

Risk if Not Fixed

Complete credential theft

An attacker with file access to the user's machine can steal all Israeli bank login credentials, potentially draining bank accounts.

Recommendation: Generate a random 32-byte key on first run, store it in keytar. On upgrade, decrypt with old method, re-encrypt with new key, and delete old config. The scrypt salt should also be random and unique per config.
2
No Content Security Policy (CSP)
packages/renderer/index.html + security-restrictions.ts
CriticalFixed
▼

What's Wrong

The renderer's HTML has no Content Security Policy. CSP is the last line of defense against XSS (cross-site scripting) attacks. Without it, if any injected or malicious JavaScript runs in the renderer, it has unrestricted access to all IPC calls — including getConfig which returns all bank credentials.

<!-- Current index.html: NO CSP at all --> <head> <meta charset="UTF-8"> <!-- Missing: <meta http-equiv="Content-Security-Policy" ...> --> </head>

Attack Scenario

A compromised npm dependency injects a small script during build. Without CSP, this script runs in the renderer, calls getConfig() via IPC, receives all bank credentials in JSON, and sends them to an external server.

Fix Complexity

Low

Add a single <meta> tag to index.html. The CSP should allow 'self' for scripts and restrict connect-src to the Base44 API domain. Estimated: 2-4 hours including testing.

Usability Impact

None

Users will not notice any change. CSP is invisible. The only consideration is if inline styles need 'unsafe-inline' in the style-src directive (Bootstrap may require this).

Risk if Not Fixed

XSS to full credential theft

Any XSS vulnerability (even from a supply chain attack on an npm package) gives the attacker access to all financial credentials and transaction history.

Recommendation: Add to index.html:
<meta http-equiv="Content-Security-Policy" content="default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; font-src 'self'; connect-src https://moneym.base44.app; img-src 'self' data:; object-src 'none';">
3
Chromium Sandbox Disabled
packages/main/src/mainWindow.ts:31
CriticalFixed
▼

What's Wrong

The Chromium sandbox is explicitly set to false. The sandbox is one of Electron's most important security features — it prevents the renderer process from accessing the filesystem, spawning processes, or using Node.js APIs directly.

webPreferences: { nodeIntegration: false, contextIsolation: true, sandbox: false, // "Sandbox disabled because the demo of preload script // depend on the Node.js api" <-- leftover from template! webviewTag: false, }

Attack Scenario

Without the sandbox, a renderer exploit (via XSS, malicious dependency, or Chromium vulnerability) can access Node.js APIs. This means the attacker can read/write any file, execute system commands, and completely take over the machine.

Fix Complexity

Low

Change sandbox: false to sandbox: true. The preload script already uses IPC properly and should work with sandbox enabled. Needs testing to confirm. Estimated: 2-4 hours.

Usability Impact

None

Zero user-facing change. The sandbox is a background security boundary. If the preload script correctly uses ipcRenderer (which it does), everything continues to work identically.

Risk if Not Fixed

Full system compromise

A single renderer exploit goes from "can read page content" to "can execute arbitrary code on the user's operating system." This is the difference between a contained and uncontained breach.

Recommendation: Set sandbox: true in mainWindow.ts. Test that all IPC calls still work. If the preload needs Node.js APIs that sandbox blocks, refactor those calls to go through IPC to the main process.
4
Unsigned Auto-Updates
electron-builder.yml + packages/main/src/handlers/updater.ts
Critical
▼

What's Wrong

The app downloads and installs updates automatically from GitHub without any code signing or cryptographic signature verification. The build config has no signing certificate, and the updater code doesn't validate signatures.

// updater.ts autoUpdater.autoDownload = true; // auto-downloads updates autoUpdater.autoInstallOnAppQuit = true; // auto-installs on restart // No signature verification configured // electron-builder.yml publish: - provider: github // No certificateFile or signing config

Attack Scenario

A man-in-the-middle attacker (on the user's WiFi, corporate network, or ISP level) intercepts the update download from GitHub and replaces it with a malicious installer. The app installs it without verification. The malicious version steals all bank credentials on next launch.

Fix Complexity

High

Requires purchasing a Windows code signing certificate (~$200-400/year), setting up the signing pipeline in CI/CD, and configuring electron-updater to verify signatures. Estimated: 2-4 days including certificate procurement and CI setup.

Usability Impact

None

Users will actually see a better experience: Windows SmartScreen warnings will disappear for signed apps, making the install smoother. Updates continue to work the same way.

Risk if Not Fixed

Complete app takeover

Attacker can replace the entire application binary, gaining persistent access to all user data and the ability to execute arbitrary code on the user's machine.

Recommendation: Purchase a code signing certificate (e.g., from DigiCert, Sectigo). Configure electron-builder to sign both the installer and the update. electron-updater will automatically verify signatures when the build is signed. Until then, consider disabling autoDownload and prompting the user to download from the GitHub releases page directly.

5
Bank Credentials Sent to Renderer via IPC
packages/main/src/handlers/configHandlers.ts
HighFixed
▼

What Was Wrong

The getConfig IPC handler sent the entire decrypted config object to the renderer — including bank login credentials (usernames, passwords, card numbers), YNAB tokens, and Google OAuth tokens. The renderer process should never have access to raw credentials.

// BEFORE (vulnerable): export async function getConfigHandler(): Promise<string> { const config = await getConfig(); return JSON.stringify({ config }); // ALL credentials included! }

How It Was Fixed

Three-pronged approach: (1) sanitizeConfigForRenderer() strips all loginFields, YNAB tokens, and Google credentials before sending config to the renderer, replacing them with a hasCredentials boolean flag. (2) updateConfigHandler() now performs a credential-preserving merge — incoming credential-stripped config is merged with the disk config so auto-save never destroys credentials. (3) A dedicated updateImporterCredentials IPC handler lets the EditImporter form send credentials directly to the main process without entering the MobX store. A config-file mutex prevents race conditions between concurrent writes.

// AFTER (fixed): function sanitizeConfigForRenderer(config: Config): Config { const sanitized = structuredClone(config); for (const account of sanitized.scraping.accountsToScrape) { account.hasCredentials = Object.values(account.loginFields).some((v) => v.length > 0); account.loginFields = {}; // credentials never reach renderer } return sanitized; } // Dedicated credential write — bypasses renderer MobX store entirely export async function updateImporterCredentialsHandler(_, accountId, loginFieldsStr) { return withConfigLock(async () => { const config = await getConfig(); const account = config.scraping.accountsToScrape.find((a) => a.id === accountId); account.loginFields = JSON.parse(loginFieldsStr); await updateConfig(configFilePath, config); }); }
Fix Complexity

Medium

Required changes across 9 files: main handlers, preload bridge, type definitions (3 files kept in sync), MobX store, and EditImporter UI component.

Usability Impact

Minor

Account settings now show empty credential fields with a “credentials saved” indicator instead of pre-filled passwords. Users only need to enter credentials when making changes.

Residual Risk

Mitigated

Renderer never receives raw credentials. New account creation briefly holds user-typed credentials in MobX (acceptable — already in DOM). Existing account credentials never enter renderer memory.

Renderer Can Inject Scrape Configuration
packages/main/src/handlers/index.ts:141-149
HighFixed
▼

What's Wrong

The scrape IPC handler accepts an optional Config object directly from the renderer, including bank credentials. A compromised renderer could send modified credentials pointing to an attacker-controlled fake banking site.

ipcMain.on('scrape', async (event, configFromRenderer?: Config) => { const config = configFromRenderer || (await getConfig()); // Uses config credentials to log into banks... });
Fix Complexity

Low

Remove the configFromRenderer parameter. Always load config from disk in the main process. Estimated: 2-4 hours.

Usability Impact

None

No user-facing change. The config is always loaded from disk anyway when no parameter is provided. The renderer just needs to save config first, then trigger scrape.

Risk if Not Fixed

Credential redirect attack

Attacker could redirect bank login to a phishing server that captures real credentials mid-scrape.

Sensitive Data in Plaintext Log Files
packages/main/src/backend/eventEmitters/loggerEmitter.ts:9-11
High
▼

What's Wrong

The logger emitter logs ALL event data (including full transaction objects with amounts, descriptions, and account numbers) to plaintext log files on disk. The getLogsInfo IPC handler then makes these logs available to the renderer.

loggerEmitter.onAny((eventName, eventData) => { logger.info(`${eventName}:`, eventData); // Logs EVERYTHING });
Fix Complexity

Medium

Add a sanitization layer that redacts sensitive fields (transaction details, account numbers, credential errors) before logging. Create an allowlist of safe-to-log fields. Estimated: 1 day.

Usability Impact

Minor

The logs viewer in the app will show less detail. Debugging will require looking at log files directly (which is rare for end users). Transaction counts and status will still be logged.

Risk if Not Fixed

Financial history exposure

Anyone with access to the log files can see the user's complete transaction history — amounts, merchants, dates, and partial account numbers.

8
Transactions Stored as Plaintext JSON
packages/main/src/backend/export/outputVendors/json/json.ts
High
▼

What's Wrong

All scraped transactions (dates, amounts, merchant names, categories, account numbers) are saved as a human-readable JSON file with default file permissions. Any program or user on the machine can read the complete financial history.

await fs.writeFile(filePath, JSON.stringify(sorted, null, 4)); // Result: a plaintext file like: // { "date": "2026-04-01", "description": "Supermarket", "amount": -450.00, "accountNumber": "12345678" }
Fix Complexity

Medium

Encrypt the JSON file using the same encryption module (after fixing Finding #1). The file would be decrypted only when needed (for Base44 sync or viewing). Estimated: 1-2 days. Alternative: use OS-level file permissions to restrict access (simpler but less secure).

Usability Impact

Moderate

This is the biggest usability tradeoff. Currently, users can open the JSON file in any text editor or import it into Excel/spreadsheets. Encryption would break this workflow. Consider offering both encrypted (default) and plaintext (opt-in with warning) export modes.

Risk if Not Fixed

Financial privacy breach

Malware, other users on a shared computer, or a stolen laptop exposes the user's entire financial transaction history.

9
Preload Script Bypasses contextBridge
packages/preload/src/eventsBridge.ts
High
▼

What's Wrong

The preload script directly imports and uses electron.ipcRenderer and electron.shell without wrapping them through contextBridge.exposeInMainWorld(). This is the Electron-recommended pattern for exposing safe APIs. The current approach, combined with sandbox: false, means the renderer has broader access to Electron internals than intended.

Fix Complexity

Medium

Wrap all exports with contextBridge.exposeInMainWorld('api', { ... }) and update the renderer to use window.api.* instead of direct imports. Note: the project uses unplugin-auto-expose which may handle this partially. Estimated: 1-2 days including renderer updates.

Usability Impact

None

Zero user-facing change. This is purely an internal refactor of how the preload exposes APIs.

Risk if Not Fixed

Expanded attack surface

The renderer has access to more Electron APIs than necessary, increasing the blast radius of any XSS vulnerability.

10
Deep-Link CSRF Bypass (Optional State Parameter)
packages/main/src/backend/auth/base44Token.ts:26
HighFixed
▼

What's Wrong

The deep-link CSRF protection treats the state parameter as optional. If the attacker sends moneymoney://auth?token=ATTACKER_TOKEN (without a state param), the validation passes as long as the user clicked "Connect" within the last 5 minutes.

export function validateAuthNonce(state: string | null): boolean { if (!pendingAuthNonce) return false; // ... if (state && state !== pendingAuthNonce.nonce) return false; // ^ If state is null/undefined, this check is SKIPPED entirely! pendingAuthNonce = null; return true; }

Attack Scenario

1. User clicks "Connect to MoneyMoney" in the app (generates nonce).
2. Within 5 minutes, attacker tricks user into clicking a malicious link: moneymoney://auth?token=ATTACKER_TOKEN.
3. The nonce exists and state is absent, so validation passes.
4. The attacker's token is saved — all future syncs send the user's financial data to the attacker's account.

Fix Complexity

Low

One-line fix: change if (state && state !== pendingAuthNonce.nonce) to if (!state || state !== pendingAuthNonce.nonce). This makes the state parameter mandatory. Estimated: 30 minutes including testing.

Usability Impact

None

The Base44 website already sends the state parameter back. This fix only rejects malicious deep links that omit the state — the legitimate flow is unaffected.

Risk if Not Fixed

Token injection / data redirect

An attacker can hijack the user's Base44 connection and redirect their financial data to an account the attacker controls.

Recommendation (one-line fix):
if (!state || state !== pendingAuthNonce.nonce) return false;

HTTPS Not Enforced in Development Mode
packages/main/src/backend/export/outputVendors/json/json.ts:50-54
MediumFixed
▼

What's Wrong

The HTTPS check for Base44 API calls is skipped in development mode. If a dev build is accidentally used in production, or the Base44 URL is changed to HTTP, Bearer tokens and financial data are sent unencrypted.

if (urlObj.protocol !== 'https:' && !import.meta.env.DEV) { reject(new Error('BASE44 URL must use HTTPS')); // Skipped entirely in DEV mode! }
Fix Complexity

Low

Remove the !import.meta.env.DEV condition. Always enforce HTTPS. Use localhost exception if needed for local testing. Estimated: 1 hour.

Usability Impact

None

No impact on users. Only affects developers who might want to test with HTTP locally (they can use localhost exception).

Risk if Not Fixed

Token interception in dev

Bearer tokens sent over unencrypted HTTP can be captured by network sniffers.

No Certificate Pinning for API Calls
packages/main/src/backend/export/outputVendors/json/json.ts
Medium
▼

What's Wrong

API calls to Base44 use standard HTTPS without certificate pinning. A compromised Certificate Authority, a corporate SSL-inspection proxy, or a sophisticated MitM attack could intercept the HTTPS traffic.

Fix Complexity

Medium

Implement certificate pinning by storing the expected certificate fingerprint and validating it on each request. Needs updating when the server certificate rotates. Estimated: 1 day.

Usability Impact

Minor

Users behind corporate SSL-inspection proxies won't be able to sync to Base44. These users would need a bypass option (with warning).

Risk if Not Fixed

MitM token theft

Sophisticated attacker on the network can steal Bearer tokens and financial data.

16
Legacy Decryption Uses Deprecated API
packages/main/src/backend/configManager/encryption/crypto.ts:51
Medium
▼

What's Wrong

Old config files encrypted with the legacy format use crypto.createDecipher(), which is deprecated in Node.js because it uses MD5-based key derivation (very weak). New configs use the v2 format with proper scrypt + IV, but the legacy path remains for backward compatibility.

// Legacy fallback: old format encrypted with crypto.createDecipher const decipher = crypto.createDecipher(ALGORITHM, salt); // DEPRECATED!
Fix Complexity

Medium

Add auto-migration: when a legacy config is detected, decrypt it with the old method, re-encrypt with v2, and save. After a few releases, remove the legacy code path entirely. Estimated: 1 day.

Usability Impact

Minor

Transparent migration on app start. Only affects users who haven't opened the app in a long time (still using legacy config format). They may see a brief delay on first launch.

Risk if Not Fixed

Weak encryption for old users

Users with old config files have their credentials protected by weak MD5-based key derivation.
